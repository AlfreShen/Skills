# skill-rules

給人讀的說明。模型照 `SKILL.md` 做事，不讀這份。

## 使用場景

- 建立、修改或審查 `SKILL.md`，包括外掛裡的 skill
- 把一套工作流程做成 skill
- 使用者修正了某個 skill 的輸出，而這個修正可能該放進 skill
- 使用 skill-creator 或其他建 skill、建外掛的 skill 時，一併載入

## 功能

- 開工前先讀完整個 skill 資料夾與說明它的 README，並讀同一外掛或市集裡其他 skill 的專案自訂段、用語與 `description`
- 逐行判斷放哪裡：換了專案還成立嗎？執行這項工作時模型需要嗎？依此決定放 `description`、本文、`references/`、`scripts/`、`assets/`、專案自己的指示、使用者自己的設定，或不放進共用 skill
- 每個固定的選擇分成三類：正確性規則、一致性要求、預設值；預設值標明並附理由，專案可覆寫
- 每個 skill 在範圍之後放「Project conventions」一節，同一外掛內字句一致；說明專案自己的指示優先，只適用於單一專案的修正放專案的指示
- 本文依工作順序排：範圍與用語、專案自訂、流程摘要、開工前、依套用時機排列的規則、最後是審查清單；一條規則只寫一處，一個概念只用一個詞
- skill 裡不放範例與案例；案例留在專案自己的指示，只把背後的通用道理寫進 skill（記錄個人品味的專案內 skill 例外）
- 內容衛生：矛盾、必要性、環境版本釘選、frontmatter 限制、引用的檔案與腳本、本文長度與結構
- 使用者修正輸出時，先分類再改：通用的改規則本身；單一專案的放專案的指示；使用者個人偏好放使用者自己的設定；不確定就問；並說明選了哪個去處
- 交付前依第 7 節的清單審查，逐項回報發現的行號與改法；使用者只要求小範圍修改時，只修改到的那幾行，其餘列出不改
- 沒有 skill-creator 之類的工具時，仍要用至少三個真實請求（含一個不應觸發的）測試，並與沒有 skill 的輸出比較

## 不處理的事

- 建 skill 的流程本身（訪談、測試案例、評測、`description` 調校、打包）：交給 skill-creator 這類工具；寫什麼、放哪裡、什麼順序、能不能放範例，以這份為準
- 從一段已收斂的工作萃取出做法或偏好：`skill-extraction`

## 專案自訂的事項

- 這份 skill 沒有「Project conventions」一節，因為它規定的正是專案可以覆寫什麼
- 單一專案的字眼、聽眾、案例、路徑與習慣，寫在該專案自己的指示（`CLAUDE.md`、Project instructions）
